Chapter 01 · Novice

What CASIROS Is

CASIROS computes financial mathematics. You describe a calculation as a graph — boxes that hold numbers, and boxes that compute formulas from other boxes — and CASIROS works out the right order to evaluate them and returns the answers.

That indirection buys you three things a spreadsheet cannot easily give you: every value is an exact decimal (never a floating-point approximation), the same model can be run thousands of times with randomised inputs, and the whole model is a JSON document you can version, share, and replay.

The pieces

ComponentWhat it doesYou'll meet it in
casiros-apiHTTP server exposing every featureChapter 02
DashboardBrowser UI for exploring the APIChapter 04
casiros-cliRuns models from files, no server neededChapter 08
casiros-workerExecutes long simulations in the backgroundChapter 12
PostgreSQLStores snapshots, audit events, and jobsChapter 10

Two vocabulary words

An input node holds a number you supply at run time. A formula node computes a value from constants and from other nodes' outputs. An edge declares that one node depends on another. CASIROS refuses to evaluate a graph containing a cycle, so a model can never depend on its own output.

Chapter 02 · Novice

Starting the Server

The fastest path is Docker Compose, which starts the API, a PostgreSQL database, a Redis cache, and the background worker together.

bash
$ git clone https://github.com/casimirex/casiros.git
$ cd casiros
$ docker compose up -d
 Container casiros-postgres  Started
 Container casiros-redis     Started
 Container casiros-api       Started
 Container casiros-worker    Started

Confirm it is alive. This endpoint needs no credentials:

bash — health check
$ curl -s http://localhost:8080/healthz
{"status":"ok"}
Verified

That response is the literal output from a running instance. If you see it, the server is up and every remaining chapter will work.

Running from source instead

Requires Rust 1.85 or newer and a reachable PostgreSQL.

bash — from source
$ docker compose up -d postgres
$ cargo run --release -p casiros-api
INFO casiros_api: CASIROS API starting on 127.0.0.1:8080
INFO casiros_api::auth: API authentication enabled with 1 key(s)
INFO casiros_api: Using Postgres snapshot, audit, and job backends

That third line is worth reading every time you start the server. It tells you which storage backend was actually selected. If it says in-memory when you expected Postgres, your configuration did not take effect — Chapter 10 explains exactly why that happens.

Chapter 03 · Novice

Your First Calculation

We will compute compound growth: what does $100 become after 10 years at 5% annual interest? Two nodes — an input holding the principal, and a formula computing future value from it.

Send it:

bash — POST /evaluate
$ curl -s -X POST http://localhost:8080/evaluate \
    -H "Content-Type: application/json" \
    -H "X-API-Key: demo-key" \
    -d '{
      "nodes": [
        {"input": {"name": "principal"}},
        {"formula": {"name": "fv", "kind": {
           "formula": "future_value",
           "present_value": {"node": "principal"},
           "rate": 0.05,
           "periods": 10
        }}}
      ],
      "edges": [{"dependency": "principal", "dependent": "fv"}],
      "inputs": {"principal": "100"}
    }'

{
    "outputs": {
        "principal": "100",
        "fv": "162.88946267774414062500"
    }
}

$100 becomes $162.8894626777441406250. Note the twenty decimal places — that is an exact decimal result, not a rounded float. Note also that the principal is quoted as a string in the request. Amounts always travel as strings so that no JSON parser anywhere in the chain can quietly round them.

Anatomy of the request

FieldPurpose
nodesEvery box in the graph, input or formula
edgesDependencies — dependency is computed before dependent
inputsRun-time values, keyed by input node name
{"node": "x"}Inside a formula: read node x's output
0.05Inside a formula: a literal constant
Try this

Change "periods": 10 to 30 and re-send. You should get 432.19424317675... — the same model, a different horizon.

Chapter 04 · Novice

Reading the Dashboard

Open localhost:8080/dashboard. It is a single page of stacked panels, each mapping to one endpoint. Nothing is hidden behind menus — you can see the whole API surface at once.

  1. Set your connection

    Enter the base URL and your API key in the Connection panel, then press Check health. The key is reused by every other panel.

  2. Run the pre-loaded example

    The Evaluate panel arrives with a working future-value model already in the editor. Press Run evaluation — you will see the JSON response and a bar chart of the outputs.

  3. Edit and re-run

    The editor is plain JSON. Change a rate, add a node, press the button again. This is the fastest way to learn the request format.

Also available

/swagger-ui renders the full OpenAPI specification with try-it-now forms for every documented endpoint.

    -H "Content-Type: application/json" -H "X-API-Key: demo-key" \
    -d '{
      "nodes": [
        {"input": {"name": "equity"}},
        {"input": {"name": "debt"}},
        {"formula": {"name": "wacc", "kind": {
          "formula": "wacc",
          "equity_value": {"node": "equity"},
          "debt_value":   {"node": "debt"},
          "cost_of_equity": 0.12,
          "cost_of_debt":   0.06,
          "tax_rate":       0.21
        }}}
      ],
      "edges": [
        {"dependency": "equity", "dependent": "wacc"},
        {"dependency": "debt",   "dependent": "wacc"}

{

A blended cost of capital of 9.822%.

Chapter 06 · Practitioner

Monte Carlo Simulation

Evaluation answers "what if the principal is exactly 100?". Simulation answers "what if the principal is somewhere between 90 and 110, and I want the whole distribution of outcomes?"

You add a bindings array attaching a probability distribution to an input node, name a target node to measure, and set a universe_count — how many independent runs to execute.

bash — POST /simulate, 5000 universes
$ curl -s -X POST http://localhost:8080/simulate \
    -H "Content-Type: application/json" -H "X-API-Key: demo-key" \
    -d '{
      "nodes": [
        {"input": {"name": "principal"}},
        {"formula": {"name": "fv", "kind": {"formula": "future_value",
          "present_value": {"node": "principal"}, "rate": 0.05, "periods": 10}}}
      ],
      "edges": [{"dependency": "principal", "dependent": "fv"}],
      "bindings": [{"node": "principal",
                    "distribution": {"kind": "uniform", "low": 90, "high": 110}}],
      "target": "fv",
      "universe_count": 5000,
      "seed": 42
    }'

{
    "count":  5000,
    "mean":   "163.01840583765845255388243872",
    "median": "163.15086871094088973807864600",
    "min":    "146.61446788454777351881126269",
    "max":    "179.17610722598985879275978080"
}

Five thousand runs: the mean outcome is about 163.02, and the realistic range runs from 146.61 to 179.18. That spread is the answer a single-point evaluation cannot give you.

Reproducibility

The seed field makes runs deterministic — the same seed and the same model always produce byte-identical results. Omit it and CASIROS defaults to seed 42. Always pin the seed for anything you intend to audit.

Available distributions

KindParametersUse for
uniformlow, highEqually likely anywhere in a range
normalmean, std_devBell-curve around an expected value
fixedvaluePinning one input while others vary

How large can universe_count be?

Synchronous /simulate holds the HTTP connection open for the whole run, so keep it in the low tens of thousands. Beyond that, use the asynchronous job API in Chapter 12 — it returns immediately and executes in the background.

Saving & Reusing Graphs

A snapshot stores a graph's structure — its nodes and edges, but not its input values — under a name you choose, so you can rebuild the model later without resending the whole document.

bash — snapshot lifecycle
$ curl -s -X POST http://localhost:8080/snapshots \
    -H "Content-Type: application/json" -H "X-API-Key: demo-key" \
    -d '{"id":"retirement-model",
         "nodes":[{"input":{"name":"principal"}},
                  {"formula":{"name":"fv","kind":{"formula":"future_value",
                    "present_value":{"node":"principal"},
                    "rate":0.07,"periods":30}}}],
         "edges":[{"dependency":"principal","dependent":"fv"}]}'
{"id": "retirement-model"}

$ curl -s -H "X-API-Key: demo-key" http://localhost:8080/snapshots
{"snapshots": [{"id": "retirement-model"}]}
OperationRequest
Save (or overwrite)POST /snapshots
List allGET /snapshots
Fetch oneGET /snapshots/{id}
DeleteDELETE /snapshots/{id}
Persistence depends on backend

With the default in-memory backend, snapshots vanish when the server stops. Set the Postgres backend (Chapter 10) for anything you intend to keep. The startup log line tells you which one is live.

The Command Line

casiros-cli runs models from JSON files with no server and no database. It is the right tool for batch work, CI pipelines, and quick local checks.

bash — casiros-cli --help
$ casiros-cli --help
CASIROS command-line interface for evaluation, simulation, and graph persistence

Usage: casiros-cli <COMMAND>

Commands:
  evaluate  Evaluate a causality graph from a JSON request file
  simulate  Run a Monte Carlo simulation from a JSON request file
  validate  Validate a graph request and report node/edge/depth counts
  save      Load an engine JSON file and write a stable snapshot JSON file
  load      Load a snapshot JSON file and write an engine JSON request file
  convert   Convert between JSON, CSV, and Excel file formats
  help      Print this message or the help of the given subcommand(s)

Put a model in a file — the same JSON body you would POST to /evaluate:

bash — validate then evaluate
$ cat graph.json
{
  "nodes": [
    {"input": {"name": "principal"}},
    {"formula": {"name": "fv", "kind": {"formula": "future_value",
      "present_value": {"node": "principal"}, "rate": 0.07, "periods": 30}}}
  ],
  "edges": [{"dependency": "principal", "dependent": "fv"}],
  "inputs": {"principal": "10000"}
}

$ casiros-cli validate graph.json
{"depth":2,"edge_count":1,"node_count":2,"valid":true}

$ casiros-cli evaluate graph.json
{
  "outputs": {
    "principal": "10000",
    "fv": "76122.550426620292066481289838"
  }
}

$10,000 compounding at 7% for 30 years reaches $76,122.55. Run validate first in scripts — it catches cycles and unknown references without executing anything, and reports the graph's depth so you can spot models that have grown unexpectedly deep.

Chapter 09 · Practitioner

Errors & What They Mean

Every error returns the same shape — {"error": "..."} — with a message written to be actionable. These are real responses from a running server.

bash — four failure modes
# A depends on B and B depends on A
{"error":"Graph contains a directed cycle"}

# A formula port points at a node that was never declared
{"error":"Port references unknown node: ghost"}

# return_on_equity with equity = 0
{"error":"Formula evaluation failed at node NodeId(0):
          Division by zero in Return on Equity (ROE)"}

# An input node declared but no value supplied
{"error":"Missing required input value for node NodeId(0)"}
StatusMeaningFix
400The request or model is malformedRead the message — it names the node or port
401Missing or invalid API keyCheck the X-API-Key header
404No such resource in your tenantVerify the id and the key's tenant
429Rate limit exceededBack off, or raise the key's limit
500Server-side failureCheck server logs
On 404 versus 403

Requesting another tenant's resource returns 404, not 403. This is deliberate: a 403 would confirm the resource exists, leaking information across the tenant boundary.

Chapter 10 · Professional

Configuration

Configuration is layered. Later sources win: built-in defaults, then config/default.toml, then environment variables.

The single most common mistake

CASIROS has two families of environment variable, and they use different separators. Settings that flow through the config file layer need a double underscore after the prefix — CASIROS__BIND_ADDR, not CASIROS_BIND_ADDR.

A single underscore is not an error. It is silently ignored, and the server starts on defaults while you believe your override applied. Always confirm with the startup log line.

Family A — config file settings (double underscore)

VariableDefaultPurpose
CASIROS__BIND_ADDR127.0.0.1:8080Listen address; use 0.0.0.0:8080 in containers
CASIROS__LOG_LEVELinfoLog verbosity
CASIROS__SNAPSHOT__BACKENDmemorymemory or postgres
CASIROS__POSTGRES__URL—Database connection string

Family B — read directly (single underscore)

VariablePurpose
CASIROS_API_KEYSComma-separated valid keys; unset disables auth entirely
CASIROS_API_KEY_TENANTSKey-to-tenant mapping with optional rate limit
CASIROS_ADMIN_KEYSeparate credential for admin endpoints
CASIROS_RATE_LIMIT_RPMGlobal default requests per minute
CASIROS_API_VERSIONURL version prefix, default v1
CASIROS_OTLP_ENDPOINTOpenTelemetry collector (needs the otel build feature)
bash — a correct production environment
export CASIROS__BIND_ADDR=0.0.0.0:8080
export CASIROS__SNAPSHOT__BACKEND=postgres
export CASIROS__POSTGRES__URL=postgresql://casiros:secret@db:5432/casiros
export CASIROS_API_KEYS="key-acme,key-beta"
export CASIROS_API_KEY_TENANTS="key-acme:tenant_acme:ws_prod:600,key-beta:tenant_beta:ws_prod:120"
export CASIROS_ADMIN_KEY="rotate-me"

Then verify the backend actually changed:

bash — confirm at startup
INFO casiros_api: Using Postgres snapshot, audit, and job backends

                                config did not take effect
Chapter 11 · Professional

Keys, Tenants, and Limits

A tenant is the top-level ownership boundary; a workspace partitions data inside it. Every snapshot, job, and audit event belongs to exactly one tenant/workspace pair, and cross-tenant access is refused at the storage layer — not merely hidden in the API.

Mapping keys to tenants

CASIROS_API_KEY_TENANTS takes comma-separated entries of key:tenant:workspace, with an optional fourth field setting that key's own rate limit in requests per minute.

bash — per-key tiers
export CASIROS_API_KEYS="key-free,key-pro"
export CASIROS_API_KEY_TENANTS="key-free:tenant_a:ws_main:60,key-pro:tenant_b:ws_main:6000"
                                                        ↑              ↑
                                              60 req/min      6000 req/min

Rate limiting in action

A key limited to 3 requests per minute, called five times:

bash — hitting the limit
$ for i in 1 2 3 4 5; do
    printf "request %d -> HTTP %s\n" "$i" \
      "$(curl -s -o /dev/null -w '%{http_code}' \
         -H 'X-API-Key: rl-key' http://localhost:8099/snapshots)"
  done
request 1 -> HTTP 200
request 2 -> HTTP 200
request 3 -> HTTP 200
request 4 -> HTTP 429
request 5 -> HTTP 429

$ curl -s -H "X-API-Key: rl-key" http://localhost:8099/snapshots
{"error":"Rate limit exceeded"}
Scaling caveat

The limiter counts requests per process using a 60-second sliding window. Three API replicas therefore permit roughly three times the configured rate. A shared Redis limiter is on the roadmap; until then, size limits with your replica count in mind.

Two ways to present a key

X-API-Key: your-key or Authorization: Bearer your-key. Both are accepted; X-API-Key is checked first.

Chapter 12 · Professional

Async Jobs & Workers

Long simulations should not hold an HTTP connection open. Submit them as jobs: the API returns a job id immediately, and a separate worker process executes the run in batches, checkpointing progress as it goes.

Requirement

The worker reads jobs from PostgreSQL. If the API is running the in-memory backend, enqueued jobs are invisible to the worker and stay queued forever. Both processes must point at the same database.

Start a worker

bash — worker startup
$ export CASIROS__POSTGRES__URL=postgresql://casiros:casiros@localhost:5432/casiros
$ cargo run --release -p casiros-worker
INFO casiros_worker: Worker started, polling for jobs worker_id="worker-1941053"

Submit and follow a job

bash — full job lifecycle
$ curl -s -X POST http://localhost:8080/simulate/jobs \
    -H "Content-Type: application/json" -H "X-API-Key: demo-key" \
    -d '{"nodes":[{"input":{"name":"x"}},
                  {"formula":{"name":"fv","kind":{"formula":"future_value",
                    "present_value":{"node":"x"},"rate":0.05,"periods":10}}}],
         "edges":[{"dependency":"x","dependent":"fv"}],
         "bindings":[{"node":"x","distribution":{"kind":"uniform","low":90,"high":110}}],
         "target":"fv","universe_count":1000,"seed":42}'
{"id":"f363b830-7d41-4909-abee-1ce1560d7d5b","status":"queued"}

# seconds later
$ curl -s -H "X-API-Key: demo-key" \
    http://localhost:8080/simulate/jobs/f363b830-7d41-4909-abee-1ce1560d7d5b
{
    "id": "f363b830-7d41-4909-abee-1ce1560d7d5b",
    "status": "completed",
    "progress": {
        "universes_total": 1000,
        "universes_completed": 1000,
        "fraction": 1.0
    },
    "created_at": "2026-08-05T14:43:03.440188Z",
    "updated_at": "2026-08-05T14:43:04.266632Z"
}

Lifecycle and control

StatusMeaning
queuedAccepted, waiting for a worker to claim it
runningClaimed; batches executing, progress advancing
completedFinished successfully
failedFinished with an error; see the error field
cancelledStopped on request before completion

POST /simulate/jobs/{id}/cancel stops a queued or running job — the worker checks for cancellation before each batch, so a long run halts within one batch rather than at the very end. GET /ws/jobs/{id} opens a WebSocket that pushes a progress frame every 500 ms instead of requiring you to poll.

Known limitation

With the Postgres job store, status and progress persist correctly but the result field currently reads back as null — the aggregate is computed but not yet written to the results column. Treat status: completed with fraction: 1.0 as the completion signal for now.

Multiple workers can run against one database safely. Each claims work with FOR UPDATE SKIP LOCKED, so no two workers ever take the same job. To increase throughput, start more worker processes.

The Audit Trail

Every authenticated request writes one immutable audit event: who acted, what they did, which resource they touched, and how it turned out. The trail is append-only — there is no update or delete operation anywhere in the codebase.

bash — GET /audit
$ curl -s -H "X-API-Key: demo-key" "http://localhost:8080/audit?limit=2"
{
    "total": 2,
    "events": [
        {
            "id": "ef9c9a04-e5a1-479f-b446-245aee082894",
            "timestamp": "2026-08-05T14:34:45.926982279Z",
            "tenant_id": "tenant_demo",
            "workspace_id": "workspace_demo",
            "api_key_id": "api_key",
            "action": "job_read",
            "resource": "/simulate/jobs/287551f0-…",
            "result": "success",
            "error": null,
            "metadata": {"method": "GET", "status": "200"}
        },
        {
            "id": "f69ba357-bcb9-49d1-a0a8-3f12ec737e6f",
            "timestamp": "2026-08-05T14:34:45.828872556Z",
            "action": "job_create",
            "resource": "/simulate/jobs",
            "result": "success",
            "metadata": {"status": "202", "method": "POST"}
        }
    ]
}

What gets recorded

ActionTriggered by
evaluatePOST /evaluate
simulatePOST /simulate and streaming variants
snapshot_create / _read / _deleteSnapshot operations by HTTP method
job_create / _read / _cancelJob operations

Failures are recorded too. A 400 leaves an event with result: "error"; a 401 or 403 leaves result: "forbidden". The trail shows attempts, not just successes.

Two deliberate design choices

/healthz and /metrics are never audited — monitoring traffic would otherwise drown the trail.

Audit writes are best-effort: if the backend fails, the request still succeeds and the failure is logged to the audit.write_failed target and counted in casiros_audit_write_failures_total. An audit outage degrades observability rather than taking the API down. If your compliance posture requires fail-closed auditing, alert on that counter.

GET /audit returns only the calling key's own tenant. Page with limit (clamped to 1–1000) and offset.

Chapter 14 · Professional

Admin Operations

Admin endpoints manage tenants and keys. They are gated by CASIROS_ADMIN_KEY, presented in the X-Admin-Key header — a separate credential from any tenant API key.

Both headers are required

Admin routes sit behind the normal authentication middleware, so a request needs both a valid X-API-Key and a valid X-Admin-Key. Sending only the admin key returns {"error":"Missing API key"}, which is easy to misread as the admin key being wrong.

bash — admin authentication
# admin key only — rejected by the outer auth layer
$ curl -s -H "X-Admin-Key: admin-secret" http://localhost:8080/admin/tenants
{"error":"Missing API key"}

# API key present, admin key wrong
$ curl -s -H "X-API-Key: demo-key" -H "X-Admin-Key: wrong" \
    http://localhost:8080/admin/tenants
{"error":"Invalid or missing admin key"}

# both correct
$ curl -s -H "X-API-Key: demo-key" -H "X-Admin-Key: admin-secret" \
    http://localhost:8080/admin/tenants
{"tenants": []}

Minting a key

bash — POST /admin/keys
$ curl -s -X POST http://localhost:8080/admin/keys \
    -H "Content-Type: application/json" \
    -H "X-API-Key: demo-key" -H "X-Admin-Key: admin-secret" \
    -d '{"tenant_id":"tenant_demo","workspace_id":"workspace_demo"}'
{
    "id":  "49a41368-3f01-4fd5-9387-be7602a13fee",
    "key": "e754ceb9-120c-4f0f-a8d2-21bc6eee41c4"
}

The raw key is shown once. Capture it immediately — it is what the client presents as X-API-Key. The id is what you use to revoke it later.

Maturity

The admin endpoints authenticate correctly and return well-formed responses, but their persistence is not yet wired to the database — listings return empty and stats return zeros. Treat this surface as provisional. For production key management today, use CASIROS_API_KEY_TENANTS and the rotation procedure in Chapter 16.

Chapter 16 · Professional

Production Deployment

Pre-flight checklist

  1. Bind to all interfaces

    CASIROS__BIND_ADDR=0.0.0.0:8080. The default binds to localhost only and will be unreachable from outside a container.

  2. Select the Postgres backend

    CASIROS__SNAPSHOT__BACKEND=postgres plus CASIROS__POSTGRES__URL. Confirm the startup log line before declaring the deploy healthy.

  3. Set API keys

    If CASIROS_API_KEYS is unset, authentication is disabled entirely and every request is accepted. The server warns at startup; treat that warning as a release blocker.

  4. Map keys to tenants

    Without CASIROS_API_KEY_TENANTS, all keys collapse into one shared default tenant and see each other's data.

  5. Set a strong admin key

    An unset CASIROS_ADMIN_KEY makes admin endpoints return 403 — safe by default, but you cannot use them.

  6. Run at least one worker

    Pointed at the same database. Without it, jobs queue and never execute.

  7. Point probes at /healthz

    Use it for both liveness and readiness.

Migrations

With the Postgres backend, migrations run automatically at startup — four files covering snapshots, tenants and workspaces, the audit log, and the job queue. For blue/green deploys, run them out of band first so old and new pods share a schema.

Rotating a key without downtime

  1. Add the new key alongside the old

    Both listed in CASIROS_API_KEYS; redeploy.

  2. Migrate clients

    Move traffic to the new key at your own pace.

  3. Confirm the old key is idle

    Check the audit trail for its api_key_id.

  4. Remove the old key

    Redeploy once more.

Troubleshooting

Jobs stay queued forever

Almost always one of three things. Check in this order:

CheckHow
Is a worker running?Look for Worker started, polling for jobs
Is the API on Postgres?Startup log must say Postgres … backends
Same database?Compare both processes' CASIROS__POSTGRES__URL
bash — is the job actually in the database?
$ docker exec casiros-postgres \
    psql -U casiros -d casiros -c "SELECT id, status FROM simulation_jobs;"
 id | status
----+--------
(0 rows)      ← empty means the API never wrote it —
               it is running the in-memory backend

Configuration changes have no effect

You almost certainly used a single underscore where the config layer needs two. CASIROS_SNAPSHOT__BACKEND is ignored; CASIROS__SNAPSHOT__BACKEND works. Re-read Chapter 10 and verify via the startup log.

Everything returns 401

Confirm the key is listed in CASIROS_API_KEYS and that you are sending X-API-Key. For admin routes, remember both headers are required.

Unexpected 429s at low traffic

Check the key's fourth field in CASIROS_API_KEY_TENANTS; a missing value falls back to CASIROS_RATE_LIMIT_RPM, which defaults to 60. Remember the window is a rolling 60 seconds, not a calendar minute.

Snapshots disappear on restart

You are on the in-memory backend. See Chapter 10.

Cross-tenant reads return 404

Working as designed. Each key sees only its own tenant's data, and a missing resource is indistinguishable from a forbidden one by design.
